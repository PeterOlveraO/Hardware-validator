# Hardware Validator v0.2.0 specification

Status: proposed implementation contract for v0.2.0.

## Relationship to v0.1.0

This document is an additive specification. The v0.1.0 inventory contract in
`docs/v0.1.0-specification.md` remains normative except where this document
explicitly defines the new CPU test command. Existing public inventory models,
detection states, sources, output, and behavior must remain compatible.

These commands must continue to perform inventory only:

```text
hardware-validator
hardware-validator --verbose
python -m hardware_validator
python -m hardware_validator --verbose
```

Inventory execution must never start a CPU test. A CPU test starts only through
one of these explicit command forms:

```text
hardware-validator test cpu
python -m hardware_validator test cpu
```

## Command-line contract

The CPU test supports:

```text
hardware-validator test cpu
hardware-validator test cpu --duration 10m
hardware-validator test cpu --load 60
hardware-validator test cpu --max-temperature 85
hardware-validator test cpu --allow-no-temperature
hardware-validator test cpu --verbose
```

The same options apply to `python -m hardware_validator test cpu`. Test options
belong to the `test cpu` command and must not alter inventory options.

| Option | Default | Accepted values |
| --- | --- | --- |
| `--duration` | `10m` | 10 seconds through 24 hours, inclusive |
| `--load` | `60` | Integer percentage from 10 through 90, inclusive |
| `--max-temperature` | `85` | Finite Celsius value from 50 through 100, inclusive |
| `--allow-no-temperature` | disabled | Flag; permits an unmonitored start |
| `--verbose` | disabled | Flag; adds technical test details |

Duration syntax is one positive base-10 integer immediately followed by one
lowercase unit: `s`, `m`, or `h`. Compound values, fractions, signs, spaces, bare
numbers, and uppercase units are invalid. Validation occurs after conversion to
seconds; therefore `10s`, `1440m`, and `24h` are valid boundaries, while `9s`
and `25h` are invalid. The maximum is 86,400 seconds.

`--load` is the requested duty cycle of each load worker, not a guaranteed total
system utilization. Other processes can make measured utilization exceed the
target. Scheduling can also produce brief busy peaks within work windows even
though Hardware Validator never requests sustained 100% load. A load of 100 is
invalid and must not be accepted.

The command uses the positive count returned by
`psutil.cpu_count(logical=True)` at preflight, with one worker per logical
processor. It does not change affinity to obtain that count. An unavailable,
non-integer, or non-positive count is an execution error. v0.2.0 must not expose
an option for changing the worker count.

Invalid syntax, ranges, commands, or option combinations are rejected before
any worker starts and use the standard command-line error exit code.

## Execution design

The implementation must use Python's standard `multiprocessing` library and a
main-process controller. After argument validation it performs thermal and CPU
preflight, primes measurement, starts the workers, samples until a stop
condition, requests cooperative shutdown, and reaps every child before return.
Durations and scheduling use a monotonic clock so wall-clock changes cannot
extend or shorten the configured exercise.

Workers must wait behind a shared start gate after process creation. The main
process releases that gate only after preflight succeeds, measurement is primed,
and every worker has started successfully. If any start fails, the controller
requests stop and reaps the already-created workers without releasing them to do
load work. The configured duration begins when the gate is released. Actual
duration is monotonic elapsed time from that point until the selected stop
condition. Worker startup and preflight are not counted as test duration.

Each worker must:

- Run repeated short work-and-wait cycles. A nominal cycle of 100 milliseconds
  is the reference design.
- Spend approximately `cycle * load / 100` doing bounded scalar arithmetic and
  the remainder in interruptible waiting.
- Check the shared stop signal frequently during both work and wait portions.
- Keep only fixed-size arithmetic and control state; it must not allocate growing
  buffers or make memory use part of the exercise.
- Exit normally when cooperative cancellation is requested.

Worker-process overhead and fixed control objects are unavoidable, but the
workload itself must use negligible additional memory and remain `O(workers)`.
It must not reserve arrays or buffers proportional to duration or available RAM.

The CPU exercise must perform no storage writes, network connections, DNS
queries, external commands, or external applications. It must not alter CPU
affinity, scheduling priority, governor, frequency, overclocking, processor
configuration, `/proc`, or `/sys`. Linux files used by the test are read-only.
Root must not be required or requested.

Load must stop when any of these conditions occurs:

- The configured duration expires.
- A monitored temperature reaches its effective limit.
- A test that began with monitoring loses all usable monitored sensors.
- A worker exits unexpectedly or cannot be started.
- A required measurement or internal operation fails.
- The main process receives supported interruption through `SIGINT` or
  `SIGTERM`.

## Temperature monitoring

Only these local, read-only sources are permitted:

- `psutil.sensors_temperatures()`.
- `/sys/class/thermal`.
- `/sys/class/hwmon` only when implementation documentation justifies a needed
  channel or critical-limit mapping that the existing selected sources cannot
  provide. It must not be added merely to broaden probing or duplicate sensors.

The implementation must assign each monitored channel a stable identity based
on its source and channel metadata and deduplicate the same physical channel
when sources overlap. A channel is usable only when its identity is
structurally valid and its current Celsius value is numeric, finite, and not a
boolean. Linux millidegree-Celsius values are divided by 1000. Malformed,
unreadable, and non-finite channels are excluded and produce a non-fatal warning
unless their loss triggers a safety stop.

A sensor may be called a CPU sensor only when source metadata, a thermal-zone
type, or an explicit device/channel relationship provides sufficient evidence.
Names, ordering, temperature magnitude, or assumptions about the host are not
sufficient. If CPU ownership is uncertain, output must use the term
"monitored temperature sensors", not "CPU temperature".

All structurally usable local temperature channels may form the monitored set;
CPU attribution is not required by this version. A non-CPU or unattributed
channel can therefore provide an additional conservative stop condition, but
its presence is not evidence that CPU package temperature is known. Output must
make that distinction and must not imply direct CPU thermal coverage when the
source does not establish it.

A finite critical limit is reliable only when the source explicitly associates
it with the same monitored channel as a critical threshold. Generic `high`,
alarm, or unrelated trip values are not substitutes. For each channel, the
effective limit is the lower of the user-configured maximum and its reliable
critical limit. The configured value must never be described as an official
manufacturer specification.

### Preflight

Before workers start, the main process must:

1. Read and validate all candidate temperature channels.
2. Establish the monitored sensor set and each effective limit.
3. Refuse to start and return `temperature_limit` if any usable current value is
   at or above its effective limit.
4. Refuse to start and return `error` when no usable current measurement exists,
   unless `--allow-no-temperature` was supplied.

No load worker may start in either refusal case. With
`--allow-no-temperature`, the command must write a clear warning to stderr before
starting and retain that warning in the final result. The warning must state
that thermal protection by Hardware Validator is unavailable. A test that starts
without monitoring is not later classified as sensor loss merely because no
sensor appears.

### Runtime monitoring

Temperature has a one-second target sampling interval. Under normal scheduler
operation the controller must not intentionally allow more than two seconds
between temperature attempts. If a test that began with monitoring cannot
complete a usable temperature round within two seconds of the previous one, it
is treated as loss of monitoring and stopped with `error`. Threshold crossings
between observations cannot be detected retroactively; once an observed channel
is at or above its limit, cooperative stop is requested without another work
cycle.

Sensor identities are the set established at preflight. New channels do not
silently replace lost channels. A missing or invalid channel is unavailable for
that sample; losing a subset is a warning, while losing all usable monitored
channels in one sampling round causes an immediate cooperative stop with
`error`. A channel reaching or exceeding its effective limit causes
`temperature_limit`.

For each monitored channel, retain minimum, maximum, and last valid temperature.
The result-level initial temperature is the maximum valid preflight reading, and
the result-level maximum is the maximum valid reading observed across all
monitored channels. Per-channel values remain available for verbose output.

## Measurement contract

The main process samples approximately once per second and records:

- Total CPU utilization.
- Per-logical-processor utilization only for `--verbose` presentation.
- Current frequency when available.
- Minimum, maximum, and last temperatures for monitored sensors.
- Monotonic elapsed time.
- Number of valid utilization samples.
- Worker liveness and unexpected exits.

Before load starts, the main process must call non-blocking
`psutil.cpu_percent(interval=None)` to initialize its measurement baseline. The
first value is discarded and must never contribute to sample count or
statistics. If verbose per-processor measurement requires a separate priming
call, that first value is also discarded. Subsequent periodic calls remain
non-blocking; the injected scheduler controls the interval.

A valid total-utilization sample is numeric, finite, non-boolean, and from 0
through 100 percent, inclusive. Failure or structural invalidity of this
required measurement stops the test with `error`. Arithmetic mean, minimum, and
maximum use only valid post-priming total-utilization samples. Zero is valid. If
no valid sample exists, utilization statistics are unknown rather than zero.

Frequency uses local `psutil.cpu_freq(percpu=True)` observations. Positive,
finite current MHz values are converted to hertz. For each observation, the
aggregate current frequency is the arithmetic mean of usable logical-processor
values. The result stores the initial aggregate before load and the minimum and
maximum aggregate observed during the exercise. Missing or malformed frequency
data is optional, produces unknown fields, and does not stop load. Verbose output
may additionally show usable per-processor frequencies.

The controller checks worker state independently of metric validity. Any worker
that exits before cooperative stop was requested is an unexpected failure,
regardless of exit code, and causes `error`. Worker-state transitions are
reported only in verbose mode unless they are errors.

## Cooperative cancellation and signals

The main process owns cancellation. A shared `multiprocessing.Event` or
equivalent cooperative primitive communicates stop requests. Worker wait periods
must use an interruptible event wait rather than an unconditional sleep.

On normal completion, thermal stop, measurement failure, worker failure,
`Ctrl+C`, or `SIGTERM`, the main process sets the cooperative signal outside any
OS signal handler and waits no more than five seconds in total for responsive
workers. It joins and reaps every exited worker. Only after that bounded grace
period may it use `terminate()` on a non-responsive worker. If a bounded join
after termination still leaves a worker alive, the controller may use
`Process.kill()` as the final platform-supported escalation and must then reap
it. Forced termination or killing is abnormal, is recorded as a warning, and is
never the normal cancellation mechanism. Inability to reap a child is an
execution error; the controller must not report normal completion or abandon a
live child through a normal return.

The main process installs handlers for `SIGINT` and `SIGTERM`. A handler may only
record the signal in minimal process-local state; it must not print, join,
terminate, acquire multiprocessing locks, or perform cleanup. The regular main
loop observes that state, requests cooperative stop, and performs all output and
cleanup. Workers must not independently handle terminal interruption in a way
that bypasses main-process cleanup.

`Ctrl+C` produces `cancelled` and exit code 130. `SIGTERM` produces `cancelled`
with a system-termination reason and exit code 1. Repeated signals must not skip
cleanup. If a worker also fails during cancellation, the primary cancellation
state is retained and the cleanup failure is recorded as a warning; an
unexpected worker exit detected before cancellation remains `error`.

## Independent public result

CPU testing must not reuse the inventory's internal `DetectionStatus` or
`DetectionResult`. It requires an independent typed `CpuTestResult` with a
status drawn from:

- `completed`: the configured duration elapsed.
- `cancelled`: interruption was requested by the user or operating system.
- `temperature_limit`: a monitored sensor reached its effective limit.
- `error`: measurement, sensor-loss, worker, or internal execution failure.

The v0.1.0 integer rule applies to inventory models, not to this independent test
result. Test percentages, temperatures, elapsed time, and aggregate frequency
may be finite floats; unknown optional test values are `None`. Display rounding
must not modify stored values. The result must be able to contain:

| Field | Type and meaning |
| --- | --- |
| `status` | `Literal["completed", "cancelled", "temperature_limit", "error"]` |
| `reason` | Non-empty `str` |
| `requested_duration_seconds` | Positive `int` |
| `actual_duration_seconds` | Non-negative finite `float` |
| `requested_load_percent` | `int` from 10 through 90 |
| `worker_count` | Non-negative `int` |
| `sample_count` | Non-negative `int` |
| `utilization_average_percent` | Finite `float | None` |
| `utilization_minimum_percent` | Finite `float | None` |
| `utilization_maximum_percent` | Finite `float | None` |
| `initial_temperature_celsius` | Finite `float | None` |
| `maximum_temperature_celsius` | Finite `float | None` |
| `initial_frequency_hz` | Positive finite `float | None` |
| `minimum_frequency_hz` | Positive finite `float | None` |
| `maximum_frequency_hz` | Positive finite `float | None` |
| `warnings` | Ordered `tuple[str, ...]` of non-fatal warnings |

Typed per-sensor statistics and periodic verbose samples may be separate nested
objects, but must use immutable deterministic collections and explicit unknown
values. The result is a test outcome, not an inventory component.

The controller resolves each iteration deterministically. It first consumes a
pending `SIGINT` or `SIGTERM`; otherwise it checks unexpected worker exits,
required measurement and sensor-loss errors, observed thermal limits, and
duration expiry, in that order. Once selected, the primary status is immutable.
A worker exit detected after a cancellation request is a cleanup warning rather
than a new primary result. Cleanup warnings do not replace `cancelled` or
`temperature_limit`; failure to clean up after an otherwise normal duration is
`error`.

The words `PASS`, `FAIL`, `healthy`, or "stable" must not describe the result,
and the command must not claim that the CPU is in good condition. `completed`
means only that the exercise reached its configured duration under the selected
conditions. It does not certify processor health, stability, cooling capacity,
reliability, or remaining life.

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Status `completed` |
| `1` | Thermal limit, sensor loss, worker failure, `SIGTERM`, or execution error |
| `2` | Invalid command-line arguments |
| `130` | Cancellation through `Ctrl+C` |

An inability to start safely because temperatures are unavailable without the
override is an execution error and returns 1. Reaching a thermal limit before
workers start also returns 1. Output encoding or write failures return 1 after
best-effort cooperative cleanup.

## Presentation

Normal stdout contains:

- Processor model when locally available, otherwise `Unknown`.
- Requested duration and load.
- Worker count.
- User-configured thermal limit and any lower sensor-effective limit without
  describing either as a manufacturer specification.
- A compact periodic line approximately once per valid sample.
- A final result with status, reason, actual duration, sample count, aggregate
  utilization, available temperature/frequency summary, and the statement that
  the exercise is not a health certification.

The compact periodic line must include elapsed time and total utilization, plus
current frequency and monitored temperature when available. Values that are not
available are printed as `Unknown`; absence must not be represented as zero.

`--verbose` adds one technical record per sampling round with:

- Sample sequence, elapsed time, interval since the previous sample, and the
  effective samples-per-second rate.
- Per-logical-processor utilization.
- Available aggregate and per-processor frequencies.
- Every monitored sensor identity, current value, effective limit, and retained
  minimum/maximum/last values.
- Worker start, cooperative-stop, exit, and forced-cleanup transitions.
- Technical reasons and affected source identities for any stop.

Warnings and errors go to stderr, including the mandatory
`--allow-no-temperature` warning. Progress and the final human-readable result go
to stdout. The command creates no report, log, or other file automatically.
Ordinary shell redirection of stdout and stderr must continue to work.

## Out of scope

v0.2.0 does not add:

- RAM, storage, GPU, network, or combined tests.
- Benchmarks, scores, or comparisons with other processors.
- Overclocking or fan control.
- Frequency, governor, priority, or CPU-affinity changes.
- UI, TUI, JSON, telemetry, or remote services.
- External commands or applications such as `stress`, `stress-ng`, `sysbench`,
  or `sensors`.
- Root execution requirements.
- Automatically created files, reports, or logs.

## Automated test strategy

Automated tests must not generate prolonged real CPU load. The architecture must
allow deterministic substitution of:

- Monotonic clock.
- Waiting/scheduling function.
- Worker factory and worker state.
- Total and per-processor utilization source.
- Frequency source.
- Temperature source.
- Signal registration and pending-signal source.

Unit and integration fixtures must cover:

- Duration syntax and lower/upper boundaries.
- Load validation, including rejection of 100%.
- Temperature-limit validation and non-finite sensor values.
- Discarding initial `cpu_percent()` values.
- Requested work/wait proportions and interruptible waits per cycle.
- Normal duration completion.
- Temperature limit before start and during execution.
- Missing sensors with and without `--allow-no-temperature`.
- Partial and complete runtime sensor disappearance.
- Worker startup failure and unexpected worker exit.
- Partial-start cleanup without release of the load start gate.
- `Ctrl+C` and `SIGTERM` paths.
- Responsive and non-responsive worker cleanup.
- Terminate/kill escalation and reaping failure behavior.
- No live or unreaped child processes after every outcome.
- Utilization, temperature, frequency, elapsed-time, and sample statistics.
- Unknown optional values and zero as a valid measurement.
- Compact and verbose output, stderr separation, and control-character safety.
- Every documented exit code.
- Complete v0.1.0 inventory CLI and output compatibility, including proof that
  inventory-only commands never construct test workers.
- No external command execution, network connection, storage write, `/proc` or
  `/sys` modification, or automatic file creation.

Parser, controller, statistics, presentation, and cleanup tests use fake clocks,
fake samples, and fake workers. A worker-loop unit test may execute only a
bounded synthetic cycle with injected timing; no automated test may depend on a
real multi-second load or host-specific utilization or temperature.

## Completion criteria

1. Preserve every inventory-only v0.1.0 behavior and require the explicit
   `test cpu` command for load.
2. Enforce all argument, source, safety, result, presentation, and exit-code
   rules in this specification.
3. Stop and reap all workers for every completion, safety, failure, `SIGINT`, and
   `SIGTERM` path without using forced termination normally.
4. Pass deterministic tests without prolonged real load or hardware-specific
   assumptions.
5. Introduce no dependency, privileged operation, external application,
   connection, storage write, automatic report, benchmark, or health claim.
